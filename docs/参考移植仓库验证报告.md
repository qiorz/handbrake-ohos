**验证方式**：不是看网页，而是 **`git clone` 两个仓库 + `git clone` 上游 HandBrake 1.11.2 + 逐文件 MD5 对比 + 二进制指纹分析**。
**验证时间**：2026-10-16
**验证结论**：见文末"总评"。

```powershell
# 三个仓库都拿到本地
```

### 1.1 目录结构 vs 上游

和上游 1.11.2 相比：**没有** `CMakeLists.txt`、**没有** `.cmake` 工具链文件、**没有** `ohos/` 目录、**没有** DevEco 工程（`build-profile.json5` / `oh-package.json5` / `.ets`）、**没有** NAPI、**没有** `*.patch`/`*.diff` 移植补丁集、**没有** 移植说明文档。
唯一的二进制产物是 `libhb/libhandbrake.a`。

### 1.2 它确实有 OHOS 适配——但只在 GTK4 前端

我用 `Select-String` 全树找 `__OHOS__`：

```
1 处  gtk\src\application.c
5 处  gtk\src\callbacks.c
6 处  gtk\src\preview.c
5 处  gtk\src\util.c
```

以及 `airbrake_ohos_*` / `AirBrake` 相关注释分布在 14 个 `gtk/src/*` 文件里。`libhb/` 和 `test/` **一处 `__OHOS__` 都没有**。

这些改动的性质是"给一个**闭源**宿主 App（AirBrake）做的桥接"：

- `gtk/src/util.c`：文件选择器改走鸿蒙系统 picker —— 通过 `dlsym(RTLD_DEFAULT, "airbrake_ohos_pick_file")` 惰性解析，符号由闭源的 `libairbrake_core` 提供（不在本仓库）。
- `gtk/src/application.c`：菜单栏交给 ArkTS（`GHB_OHOS_NATIVE_MENUBAR` 环境变量关掉 GTK 自带菜单栏），ArkTS 通过 `gtk_application_get_menubar()` 读 `GMenuModel`。
- `gtk/src/callbacks.c`：沙箱写盘用 staging + `airbrake_ohos_finalize_save(uri)` 回拷。
- `gtk/src/ffstream.c`（新增，`Copyright © 2026 AirBrake Project`）：因为鸿蒙 GTK4 用 `-Dmedia-gstreamer=disabled` 编译，`gtk_media_file_new()` 落到 `GtkNoMediaFile`，所以自己写了个 FFmpeg 版的 `GtkMediaStream`/`GdkPaintable` 做预览。
- 注释里引用的设计文档 "harmonyos-porting §7.1/§7.2" **不在仓库里**。

`gtk/src/meson.build` 里把前端改成产出 `libghb.so`（排除 `main.c`），以便宿主线程调 `ghb_application_boot`。

> **也就是说：仓库 A 的"移植"= 上游 master + 一个 GTK4 前端的宿主桥接层，且桥接的另一半（`libairbrake_core`）不开源。**

### 1.3 `libhandbrake.a` 是**真货**——用二进制指纹证明

```
llvm-ar t  -> 85 个成员（decavcodec.o / encx265.o / muxavformat.o / work.o ...）
llvm-ar x && llvm-readelf -h acompressor.o
     Class: ELF64      Machine: AArch64
llvm-readelf -p .comment acompressor.o
     [1] OHOS (dev) clang version 15.0.4 (llvm-project 99548401bd80576251755b185ab95945e5fe7884)
```

再看提到它的文件（同一份报告中独立复核得到的结论）：

```
/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/native/llvm/bin/../../sysroot/usr/include/aarch64-linux-ohos/bits
```

**结论**：libhb 是**从 macOS 上用 DevEco 自带 OHOS SDK（clang 15.0.4）+ `aarch64-linux-ohos` musl sysroot 交叉编译**出来的真·OHOS arm64 静态库。
提交进仓库的动机也看得出来：`gtk/meson.build` 用 `cc.find_library('handbrake', dirs: hb_dir / 'libhb')` 直接吃这个 `.a`，这样前端不用重编 libhb。

从它提交的 `libhb/handbrake/project.h` 还能读出他们的特性配置：

```c
#define HB_PROJECT_HOST_SPEC    "aarch64-unknown-linux-ohos"
#define HB_PROJECT_HOST_SYSTEM  "linux"
#define HB_PROJECT_HOST_SYSTEMF "Darwin"     // 注意：生成于 macOS 宿主
#define HB_PROJECT_FEATURE_ASM   0
#define HB_PROJECT_FEATURE_GTK   1
#define HB_PROJECT_FEATURE_X265  1
#define HB_PROJECT_FEATURE_LIBDOVI 0
#define HB_PROJECT_FEATURE_NVENC 0   // VAAPI/NVDEC/QSV/VCE/AMFDEC/NUMA 也都是 0
```

（顺带说明它为什么不能拿来直接用：`X265=1` 且 `GTK=1`，意味着这个 `.a` 还依赖 x265、libass、libbluray、GTK4/GLib 等一大堆库，链接条件与我们的裁剪方案不兼容。）

### 2.2 它的策略：**在鸿蒙 PC 上本地编译**，而不是交叉编译

README 里的做法（原文摘录）：

```bash
export PATH=$HOME/.harmonybrew/bin:$PATH
export LD_PRELOAD=$HOME/.harmonybrew/opt/uname-is-linux/lib/libuname.so    # 让 uname 报告 Linux
export TMPDIR=$HOME/tmp
./configure --disable-gtk --disable-numa
cd build && make -j$(nproc)
./HandBrakeCLI --version
# 如报错 Permission denied，先签名：binary-sign-tool sign -inFile ./HandBrakeCLI -outFile ./HandBrakeCLI -selfSign "1"
```

产出是 **`HandBrakeCLI` 可执行文件**（`test/test.c`），libhb 静态链进去，**没有 `.so`、没有 NAPI**。

它的环境要求里有两处很关键：

- `uname-is-linux`（[HarmonybrewGlobal/uname-is-linux](https://gitcode.com/Harmonybrew/uname-is-linux)）：一个 `LD_PRELOAD` 垫片，劫持 libc 的 `uname()` 让它返回 Linux —— 因为**鸿蒙上 `uname -s` 返回 `HarmonyOS`**，autotools/CMake 直接认不出系统类型。这与我在设备上实测到的 `uname -a` 输出完全吻合。
- `TMPDIR` 必须挪走：鸿蒙 PC 的默认临时目录在 **hmdfs** 上，该文件系统的缺陷会导致编译失败 → `export TMPDIR=/data/storage/el2/base/cache`。

### 2.3 必须指出的一个 README 与代码不一致处

README 声称在 Linux/鸿蒙上"lame/opus/speex/libvpx/x264 等 14 个包改由系统库（harmonybrew）提供，不参与构建"。
但我在仓库里**找不到任何实现这个的机制**：`make/include/main.defs` 仍然**无条件** `MODULES += contrib/lame`、`contrib/libopus`、`contrib/libspeex`、`contrib/libvpx`、`contrib/x264`（只有 `bz2/zlib/xz/iconv/regex` 是 `HAS.*` 条件化的），唯一的 contrib 改动就是那句 `umask` 的 sed。
→ 要么作者是在构建时手工覆盖 `MODULES` / 预置 `.stamp` 文件（文档里没写），要么 README 把话说大了。**不实际跑一遍无法判定。**

### 2.4 harmonybrew 支不支持平板？—— **官方支持列表里没有平板**

harmonybrew 的设备支持表（原文）：

| 形态 | 代表 | 最低系统 | CLI 环境 | 架构 | 支持等级 |
|---|---|---|---|---|---|
| 鸿蒙 PC | HUAWEI MateBook Pro | HarmonyOS 6.1.0.117 SP68 | HiShell | arm64 | Tier 2（低） |
| 鸿蒙开发板 | dayu200 (rk3568) | OpenHarmony 6.1 | hdc shell | arm64 | Tier 1（高） |

**手机、平板都没有出现。** 文档只说"理论上可以继承生态，因此也能在 HarmonyOS 上运行"，同时警告"能运行不代表完美支持……可能因系统安全限制受限，这属于系统级原生限制"。

我们的目标设备是 **MatePad Edge 平板**，且实测 `/storage/Users/currentUser`（harmonybrew 的前缀目录）在此设备上**不存在** → **仓库 B 的路线在本设备上不可用**。

## 4. 总评：能借鉴什么，不能借鉴什么

### ✅ 值得借鉴

1. **仓库 B 的 3 处构建改动**（`--disable-vulkan`、`config.guess` 的 `TMPDIR` 修正、contrib 的 `umask 077→022`）——这是"鸿蒙当 Linux 用"时已知会撞的坑的实测清单。
2. **仓库 B 证明：libhb 本体不改一行代码就能编到 OHOS**（走 `SYS_LINUX` 路径）。我的实践完全印证了这一点。
3. **`uname-is-linux` 这个垫片的存在本身就是重要情报**：鸿蒙 `uname -s` 返回 `HarmonyOS`，是 autotools 类项目的系统性障碍。
4. **仓库 A 的前端桥接模式**（如果将来做图形前端）：系统文件选择器、菜单栏交给 ArkTS、沙箱内 staging+回拷、无 GStreamer 时自写 FFmpeg 版 `GtkMediaStream`，以及它记录的两个真实崩溃（GSource payload 双重 unref 导致 UAF；`g_clear_pointer` 误用于两级指针的 FFmpeg API）。这些在 GTK4 路线下几乎一定会再遇到。
5. **仓库 A 的 `libhandbrake.a` 是一份"可行性证明"**：能读出 `OHOS (dev) clang version 15.0.4`，说明这条路（用 DevEco SDK 交叉编译 libhb）确实走得通。

### ❌ 不能直接借鉴

1. **仓库 A 的"移植"不可复现**：没有工具链配置、没有构建脚本、没有 NAPI、宿主那一半闭源；`version.txt` 还伪造了一个不存在的版本号。它更像是"AirBrake 项目的工作树快照"。
2. **仓库 B 的路线在平板上不可用**：它依赖鸿蒙 PC 的 `/storage/Users/currentUser` 与 harmonybrew，而这两者在我们的 MatePad Edge 上都不存在；且**平板无法从 shell 执行自编译二进制**（本次实测确认）。
3. **两个仓库都不涉及 HAP 打包、NAPI、签名**——而这三件事恰恰是零售鸿蒙设备上真正的门槛。
4. **两个仓库都没有做特性裁剪**：它们都是在"依赖齐全"的前提下构建的。要在 Windows 主机上从零交叉编译 26 个三方库，必须自己决定裁什么、怎么补桩——这部分**没有任何现成经验可抄**。

### 🎯 对本次移植的实际影响

本次移植最终采取的路线与两个参考仓库**都不同**：

| | 仓库 A | 仓库 B | 本次 |
|---|---|---|---|
| 宿主 | macOS | 鸿蒙 PC 本地 | **Windows + MSYS2** |
| 目标形态 | `libghb.so`（GTK4 前端）+ 预编译 `libhandbrake.a` | `HandBrakeCLI` 可执行文件 | **HAP + NAPI（`libhandbrake.so`）** |
| 依赖 | contrib 全量自举（37 包） | harmonybrew 14 个 + contrib 自举 | **自建 5 个 + 特性裁剪 + 30 个符号桩** |
| 前端 | GTK4 | CLI | **ArkTS 调 NAPI，内部复用官方 `test.c`** |
| 签名 | 未涉及 | `binary-sign-tool` 自签 | **HAP 签名（受阻于华为 profile）+ 自签链的完整实验** |

> **一句话**：网上那两个仓库能告诉你"libhb 本身不难移植"，但**没有告诉你**"在零售鸿蒙设备上它必须跑在应用沙箱里，而这个沙箱的门票是华为签名的 HAP"——那才是这次移植真正的主线。
